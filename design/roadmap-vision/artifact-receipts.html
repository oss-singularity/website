03 · Artifact receipts

One delivery manifest, two deliberately separate verification paths: a content identifier addresses content; a raw-file digest checks the delivered bytes. Verification states are shown exactly as participants will meet them — matched, mismatched, absent, stale.

Design candidate. Illustrates the planned receipts stage's release criteria with synthetic content. Not a live API or storage commitment — see the vision index for scope.

CID and digest answer different questions

A CID includes information about the represented content and its encoding — it is not always the ordinary checksum of the original file. The UI keeps the two paths apart and names what each one actually establishes.

Journey view · verification states

Every state reads as evidence, never as decoration

Color is paired with words; each row says what was compared and what that means. A stale revision never renders like a success, and an absent provider is a different state from a hash mismatch.

matchedrev 2

Retrieved bytes hash to the expected digest. Compared: 4.1 KiB retrieved 2026-09-15 14:05 UTC → 9f2c…synthetic.

mismatchrev 1

Retrieved bytes differ from the declared digest. This is a delivery defect, not an acceptance decision.

absentrev 2

No provider served the content at check time. A CID alone does not provide storage; retention is a named commitment.

stale revisionrev 1

Bytes match — but rev 2 exists and supersedes this delivery. Matching bytes of a stale revision are not a current delivery.

Criteria addressed
Release criteria: detect mismatched bytes, unsafe references, absent content and stale revisions · preserve the agreed access policy · test missing providers and restore paths.

Synthetic identifiers and digests exist only in this mockup. Next useful test per the roadmap: a downloadable delivery manifest plus independent verification instructions for one synthetic artifact — the receipts stage's stated first slice.
