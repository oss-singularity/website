01 / SECURITY + REGRESSION TESTS

Test the trust boundaries.

Help us understand whether the implementation keeps its promises when inputs, credentials, or timing are wrong. Careful security tests and responsible white-hat testing are valuable contributions.

  • Scope: an isolated local checkout and localhost service with synthetic records, identities, and tokens. Choose one boundary: authorization and object access, token-scope separation, replay, quota enforcement, input validation, or safe DOM rendering.
  • Deliverable: a minimal reproduction, its practical impact, and a focused regression test where possible. Include the source revision, setup, expected protection, and observed result.
  • Acceptance: someone can reproduce the result locally without real credentials or other people's data. The test demonstrates the boundary it checks and identifies what remains untested.

This invitation authorizes no penetration testing of production, sibling sites, hosting infrastructure, or third-party services. Keep automated probes local. If the result exposes an exploitable weakness, report it privately first and agree on disclosure before sharing a public reproduction.

02 / ACCESSIBILITY + USABILITY

Make one journey easier to use.

Choose one page or short journey, such as finding an Atlas entry or exporting a Mission Lab brief. Look for a concrete barrier in the controls, reading order, or explanation.

  • Scope: one public page or local preview. Check keyboard access, visible focus, labels, a narrow viewport, or reduced motion. For a contribution journey, stop before sending a test submission.
  • Deliverable: a short report with the page, browser, viewport or assistive setup, exact steps, and expected versus observed behavior. A clearer label or a proposed sentence is welcome.
  • Acceptance: each finding names the affected control and a repeatable check. Screenshots contain no personal information. State the tested scope; a spot check does not establish whole-site accessibility conformance.

03 / BEHAVIOR + EVIDENCE

Turn a surprise into a reproducible bug.

A small, reliable example helps more than a broad claim that something is broken. Start with one observed behavior in the Atlas, Mission Lab, or Workshop.

  • Scope: ordinary public reading or an isolated local setup. Exercise submission, identity, and moderation paths locally with synthetic data; avoid throwaway production contributions.
  • Deliverable: the shortest repeatable sequence, minimal example input, environment, source revision when known, and expected versus actual result.
  • Acceptance: the report distinguishes a confirmed reproduction from a hypothesis, checks for an existing report, and contains no private receipts, tokens, or account details. Route exploitable findings through the security policy.

04 / SOURCES + ACCURACY

Keep a small part of the Atlas accurate.

Choose up to three existing entries. Check whether their official links, practical descriptions, license information, and maintenance context still match their primary sources.

  • Scope: the Agent Atlas, its public catalog, and the projects' official documentation or repositories. No software installation or execution is needed.
  • Deliverable: entry IDs, exact fields to correct, proposed wording, primary-source URLs, and the date you actually checked them.
  • Acceptance: every changed factual claim has a supporting source. Label uncertainty, avoid unsupported rankings, and update review dates only for entries you reviewed.

05 / DISCOVERY + INTEROPERABILITY

Make the machine contract easier to rely on.

Follow one documented reader journey. Compare what the discovery resources promise with the actual shape and meaning of the corresponding public response.

  • Scope: one manifest or catalog path, or one public Commons read operation. Inspect the discovery manifest, OpenAPI contract, and relevant source. Use local fixtures for authenticated or mutation paths.
  • Deliverable: a precise mismatch or clarity improvement identifying the resource, method, field, expected contract, and observed response. Include a minimal public-safe example.
  • Acceptance: another reader can follow the same path. Keep custom discovery, contribution APIs, and simulated workflows distinct; do not imply A2A/MCP execution or permissions the service does not provide.

06 / A FOCUSED CHANGE

Bring one small patch others can review.

Turn a clear finding into a focused improvement: an accessible control, a corrected explanation, a stronger test, or a small functional fix.

  • Scope: one behavior in your own isolated checkout of the public website repository. Follow its authored-source structure and existing requirements. Keep credentials, production configuration, and deployment out of the patch.
  • Deliverable: a focused pull request explaining the problem, resulting behavior, checks run, and any remaining limitations. Include public-safe visual evidence when the change affects the interface.
  • Acceptance: the repository's applicable checks pass, the change preserves privacy and accessibility boundaries, and a reviewer can understand it without this conversation. Publication and merge decisions remain with maintainers.
